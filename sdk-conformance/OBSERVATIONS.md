# Initial three-SDK observations

TypeScript is the de facto reference. Go, Python, and the written specification
are cross-checks that can identify a bug or stale behavior in that reference.
These observations were collected from these pinned revisions:

| SDK | Revision |
| --- | --- |
| TypeScript | `197812b9e20d87315998027b0ad810ca8644c4ee` |
| Go | `ff799d9758ba019995e59d3f4bc1b2d0efa0ad92` |
| Python | `c69d9a756a61d8596e1b3284f880d19fdf75dd77` |

## Shared boundaries

All three expose an HTTP serve handler with inspection/synchronization and
invocation paths. All three also implement Event API submission, request
signature handling, and Connect. Those boundaries are better conformance
targets than public language APIs.

## Differences that must be investigated, not normalized away

The runnable matrix currently demonstrates:

- A step-free completion returns `206` with a terminal `RunComplete` opcode in
  TypeScript, but `200` with the function output in Go and Python.
- A function error returns `400` plus `X-Inngest-No-Retry: true` in TypeScript,
  while Go and Python return `500` with different serialized error shapes.
- All three produce the same deterministic hashes and opcode names for the
  step probes, but differ in optional/null fields, display names, timing,
  userland metadata, and error serialization.
- `Sleep` encodes its duration in different locations: TypeScript uses `name`,
  Go uses `opts.duration`, and Python returns an absolute timestamp as `name`.
- `WaitForEvent` puts the event name in `name` for TypeScript and Python but in
  `opts.event` for Go. Empty `if` and options fields also differ.
- Signed development-mode in-band sync succeeds in TypeScript and Go. Python
  chooses out-of-band registration and fails when no dev server is listening.
- Introspection agrees on status, schema version, mode, and function count, but
  differs in optional fields and Go reports no event key for the fixture's
  development key.
- Primary-key, fallback-key, and wrong-key handling agree. All three accept the
  two configured keys and return `401` for a wrong key.
- TypeScript rejects signatures more than five minutes in either direction.
  Go rejects old signatures but accepts signatures ten minutes in the future.
  Python accepts both ten-minute-old and ten-minute-future signatures.

The raw evidence is produced by `run-matrix.sh`; none of these differences is
yet classified as an SDK bug or an accepted compatibility profile.

These differences imply at least separate execution profiles and semantic
matchers. They also show why a real dev server cannot be the first oracle: its
chosen execution mode can turn a valid SDK exchange into an apparent failure.

## What the cloud backend and OSS dev server actually accept

This is compatibility evidence, not a declaration that every accepted legacy
shape should be generated by new SDKs. The cloud backend vendors the same HTTP
driver, opcode parser, and executor used by the OSS dev server.

| Difference | Cloud backend behavior | OSS dev server behavior | Harness classification |
| --- | --- | --- | --- |
| `200` output vs `206 RunComplete` | Any 2xx other than `206` is a successful direct function result. A `206` is parsed as one or more opcodes; `RunComplete` explicitly finalizes the run. | Same executor behavior. | Two accepted execution encodings. Assert the final output, not one status code. |
| Function error status and no-retry header | Any non-2xx is an execution error. `X-Inngest-No-Retry: true` stops retries immediately; otherwise queue attempt limits decide. For the zero-retry fixture, TypeScript's `400`/no-retry and Go/Python's `500` still all fail on the first attempt. | Same. | Observe the transport difference; add end-to-end retry-count cases before making it blocking. |
| In-band vs out-of-band sync | A response declaring `in_band` must have a valid response signature and a decodable registration body. Otherwise a successful `200` with `X-Inngest-SDK` completes the out-of-band flow. The Vercel registration path falls back to out-of-band when inspection cannot authenticate with either rotation key. | The dev server's normal ping does not request in-band sync. SDKs register by POSTing to `/fn/register`; this is why Python's dev-mode out-of-band behavior works with a real dev server even though the isolated probe has no registration receiver. | Separate cloud in-band and dev out-of-band scenarios. Do not require in-band sync in development. |
| Sleep duration location | Reads `opts.duration`, then falls back to `name`. It accepts duration strings and timestamps. | Same. | Both fields are compatible. Normalize to a semantic wake time/duration. |
| Wait-for-event name location | Reads `opts.event`, then falls back to opcode `name`; only fails when both are empty. | Same. | Both fields are compatible. Normalize to event name plus timeout/expression. |
| Opcode optional fields | Dispatch is by `op`. `StepError` must contain `error`. Operation handlers consume operation-specific fields; `displayName` falls back to `name`, and then `id`. Timing, userland metadata, omitted/null optional fields, and error formatting are not needed for dispatch. | Same. | Require `op`, a stable `id` where state is written, operation-specific semantic inputs, and `error` for `StepError`; compare the rest separately as observability metadata. |
| `X-Inngest-Req-Version` | The first SDK response persists this value for the run and later requests echo it. Missing/invalid parses as `0`, the legacy TS-specific hashing profile, which can break replay or cross-language migration. All three fixtures return `2`. | Same. | Required and blocking; compare it independently of response encoding. |
| Signature keys and freshness | Cloud sends signatures using the current Unix second and accepts primary or fallback keys. Wrong-key SDK responses are `401`. Backend trust probes treat `401` as signature verification failure. | Dev mode normally skips signature verification unless key enforcement is enabled. | Primary, fallback, and wrong-key cases are required. Freshness is disputed: TypeScript has the strongest replay protection; Go is one-sided; Python has no age check. |

The backend's own Go response-signature verifier also rejects only timestamps
older than five minutes and accepts future timestamps. Normal cloud requests
and SDK responses are stamped with the current time, so this does not break the
ordinary path, but it does mean the implementations disagree on replay/clock
skew policy. New SDK acceptance should follow TypeScript's bounded ±5 minute
window while the Go and Python behavior remains a reported security discrepancy.

## Introspection field impact

The cloud parser supports historical schemas from `2023-10-24` through
`2024-05-24`; an unknown explicit `schema_version` fails parsing. The fields do
not all have equal operational weight:

- `schema_version` selects the parser and is required for the current shape.
- `authentication_succeeded` is used to decide whether authenticated in-band
  sync is possible; missing or unsuccessful authentication causes out-of-band
  fallback in the integration flow.
- `capabilities` from an in-band response are persisted into the registration.
  TypeScript currently omits `in_band_sync` while Go and Python advertise it;
  today's selection code does not consult that capability, so registration
  still works, but the stored capability differs.
- `mode`, `function_count`, and signing-key hashes are consumed by signing-key
  rotation/health checks. A zero function count is treated as an old SDK for
  that check.
- event-key hashes and signing-key hashes drive health diagnostics, not request
  authentication. Authentication comes from the signed request/response.
- origins, app/environment identity, framework, SDK language/version, and
  serve path are informational in the inspected backend paths reviewed here.
- The OSS dev server does not use GET introspection for normal registration.

## Remaining ratification work

1. Decide whether new SDKs may emit direct `200` completion or should emit the
   TypeScript `RunComplete` profile while retaining server compatibility for
   both.
2. Decide whether top-level and step error transport must be standardized once
   end-to-end retry-count scenarios are present.
3. Fix or explicitly grandfather Go's future-signature acceptance and Python's
   lack of signature freshness validation.
4. Decide whether `capabilities.in_band_sync` is mandatory when an SDK can
   produce an in-band response.

Current TypeScript behavior supplies the default for unresolved cases. The
written SDK specification provides historical and design context. A durable
decision should be recorded alongside the vector and, where appropriate, in
the SDK specification.
