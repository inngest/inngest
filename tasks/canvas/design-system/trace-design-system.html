Trace Design System

How Inngest draws a function run. The vocabulary is in the panel on the left and is live: change it there and every figure on this page changes.

Moments

Inngest records a run as spans. A span carries timestamps: when the step was enqueued, when the SDK started executing it, when it resolved. Those timestamps are what the trace has.

Durations

The interval between two timestamps is what you want to read.

A step’s lifecycle

Every step reaches the same states whatever its type: enqueued, executing, resolved. A step that throws adds an attempt and a backoff and goes round again.

Two rules

Marks report whether something has resolved.

  • hollow: not resolved
  • filled: resolved. Only a resolution is green or red.

Bars report whether the SDK was executing.

  • solid: your function was running
  • hatched: it was not
Colour says what kind. Fill says whether the SDK was executing, for a bar, and whether it has resolved, for a mark. The full set is in the panel on the left.

Structure

A discovery request is the SDK reporting what to run next. When one reports more than one step, it gets its own bar and a ribbon down to the steps it reported.

A discovery bar appears only where the request reported more than one step. A request that reported one step, which is the next step in a chain or the step after a coalesce, is a single execution and rolls into that step’s row.

The Run row

Today the Run row is a full width bar in the run’s status colour. The header, the status badge and the axis already report that. It could instead report where the elapsed time went.

The selected row

A row is plotted against the whole run, so a step that took ten seconds inside a twenty minute run is a few pixels wide and its marks overlap. Selecting it replots that row across the full width using the same bars and marks, and names each piece: intervals with their durations, marks with what happened. Hover a piece for its description.

This is not a second way of drawing a run. Same bars, same marks, more width.

Annotations

Optional, usually a duration. The annotation sits after the row’s last bar rather than in a fixed column, so it takes no horizontal space and disappears when there is nothing to report.

Scenarios

Ordered from one step to the cases that are hard to draw. Each shows the run at rest and, where it differs, on hover or select.

Sequential

One request, one step. The SDK reports and executes in the same request, so there is no discovery bar.

Fan-out and coalesce

One request reports three steps. The ribbon threads their enqueue marks, which are blue because a discovery request put them there.

Three steps resolve and cause the next request. That request reported one step, so it rolls into that step’s row.

The ribbon covers exactly the steps the request reported, so an uneven fan-out is countable without interacting.

Fan-out inside a fan-out. One ribbon per discovery request.

Width is decided at runtime. The ribbon reports what happened and predicts nothing.

One resumption reports two steps. Both sit under one ribbon, so no order is implied between them.

Two branches that each caused their own request. Two requests, no ribbon.

Attribution

Pairings stay inside their branch. Selecting a step shows the request that reported it.

Rows sort by start time, so the order steps were reported in is not row order.

A discovery request after unrelated waits. Response order stops matching branch structure.

Promise.race(). The winner is a dependency of the next request. The loser resolved after that request started, so it has no cable.

A step started but never awaited. No outgoing cable.

Grouping inferred rather than reported by the SDK: dashed ribbon, dashed cable.

Platform time

Queue time. The step waiting for the executor to pick it up.

A discovery request is a separate execution. It happens at the start of a run and on fan-out.

Held by flow control. Amber hatched, still not SDK execution time.

Throttle, rate limit and debounce are the same fact and take the same treatment.

System latency is queue time and is labelled the same way.

Finalization keeps its own row and is not SDK execution time.

Everything Inngest did is hatched. Only SDK execution is solid.

Every millisecond between a row’s start and its resolution belongs to a named interval.

step.sendEvent() is the one row that points out of the run. The ring is hollow because those runs are not in this trace, and the count is the way into them.

The gap between a step resolving and the next request starting is drawn once, as the cable and as the interval.

Waiting

A wait that matched. Blue while it is open, green at the mark where the event arrived.

A wait that expired with no match. The run carries on: a timeout is a result the function can act on.

A wait inside a fan-out holds the level open. The next request cannot start until the slowest member resolves.

Waiting and failing must not read alike. One is hatched and never red; the other is solid and red.

Time and the axis

An idle gap that dwarfs the work is compressed and marked as a break. Only the axis changes; every duration is still wall clock.

Seven days elapsed, 62ms executing. The fill rule reports that before you have read a number.

Two tiers of axis label, so a run measured in days keeps its resolution without a second axis.

A step too short to draw is still drawn, at a minimum width, with its real duration beside it.

Scale

Five hundred sequential steps collapse to one row that reports the count and draws where each member ran.

A wide fan-out collapses the same way. The stagger of a concurrency limit is visible without expanding it.

A failure cluster two thirds through a long run is a red smear in the strip, findable without interacting.

About forty rows at rest whatever the step count, and any group expands where you are standing.

Naming and identity

The same step name on two branches. The name is not the identity; the request that reported it is.

The SDK’s :1 and :2 suffixes are not stable under parallelism, so nothing in the drawing depends on them.

Interaction

Three tiers of attention: the row, what caused it, everything else. Nothing is removed, only quietened.

The strip above the run is a minimap of the same trace, in the same order and the same colours.

Honesty

Where the trace cannot say what caused a request, it declines rather than guessing.

A row’s label and its drawing have to agree about which interval the number names.

Nothing is drawn that cannot be asked what it is. Hover any row for its parts.

Connect

Connect changes the transport, not the spans. Same span names, same shape, same step ops, so nothing above needs a Connect variant.

Two differences sit inside the spans. A Connect run carries no inngest.http.timing, so there is no network breakdown to expand. The connect proxy polls for the SDK response every 2s plus a random 0 to 3s; when its push is missed that wait lands inside the execution span with nothing marking it, so the execution figure over reports.
